# prefill 吞吐与提示词长度的关系

[English](../../benchmarks/prefill-length-sweep.md)

开发性扫描，记录于 2026-11-18，在 RTX 3090 Ti / RTX 3090 / RTX 3080 上进行，
强制功耗限制分别为 400 / 320 / 250 W，系统 RAM 为 62 GiB。它在部署状态的
服务配置上，沿一串递增的新提示词长度测量 prefill 吞吐。这些是 agent 运行的
开发性测量，不是维护者发布的头条数据，也不是质量对比。

## 结果

引擎运行于 32K 边界构建（git `f259374`，二进制 SHA-256
`bdcadb49b6530084d89b82d8cfe9c261a5502f34807d9ea5c995d59265176818`），
启用自动专家与 prefill 放置、自适应调整与磁盘驻留。除监听地址与端口外，
设置与生产单元完全一致：`--gpu 0,1,2`、int8 KV、上下文 262,144、
`--prefill 32768`、spec 8 的 DFlash2、prompt cache 4、启用磁盘会话缓存。
专家缓存稳定在 7,543 个 slot。每个数据点是一次全新请求，提示词 token 复用为零，

13.3 GB/s 主存到设备带宽上限相符，而非算力受限。对等卡的 chunk
数几乎随长度线性增长，作图时是有用的第二序列。

## 测量干扰：请求之间的专家缓存复用

24,576 token 的请求起初看起来像是一次回退：它的中位速率（2,822 tok/s）
低于两侧相邻数据点，而就绝对时间而言，它比多承载 33% token 的 32,768 token
请求还慢。每 token 成本不会随长度上升，所以该点不可能是上下文长度造成的效应。

事实也确实如此。三次重复呈双峰分布：

| 重复 | 提示词时间 | 速率 | 经 PCIe 传输的已路由专家比例 | 前一个请求 |
|---|---:|---:|---:|---|
| 0 | 8,799 ms | 2,793 tok/s | 45.2% | 16,384 token |
| 1 | 5,898 ms | 4,167 tok/s | 28.5% | 32,768 token |
| 2 | 8,709 ms | 2,822 tok/s | 48.3% | 229,376 token |

在快速模式下，24,576 token 恰好落在长度曲线上
（0.2400 ms/token，介于 16,384 token 的 0.2870 与 32,768 token 的 0.2300
之间），因此不存在拐点。中位数只是选中了被污染的那个峰，三次中有两次偏慢。

原因是专家缓存所占的 VRAM 是 KV 后备内存的弹性来源。一个长请求会把这些
slot 收回用作自身 KV，并逐出其中保存的专家；引擎把这件事记录为
`elastic KV: … the expert cache N -> M slots, K experts displaced`。
随后到来的请求因此要经 PCIe 传输其提示词路由到的专家，而不是发现它们已在
显存中。在上表的慢速重复里，前一个 229,376 token 的请求占用了 245,760 个
KV cell 并逐出 1,251 个专家，只剩 6,243 个 slot；而快速重复开始时保有完整的
7,398 个 slot。

在全部 75 次请求中，判别量是已路由专家经 PCIe 读取的比例，即
`… more read by the GPU over PCIe or from another GPU (P% of all 480 routed)`。
它与「相对于同一长度上观测到的最佳速率的差距」相关，r = −0.354（n = 50，
排除寒冷的首段）；而每次请求的 SSD 专家读取量与该差距单调相关：从文件读取
0–30 GB 的请求平均差距 4.8%，读取 80–200 GB 的平均 14.5%。入口 slot 数是
较弱的预测量（r = +0.14），因为关键在于某个提示词具体路由到的专家是否驻留，
而非有多少 slot 空闲；寒冷的首段清楚地体现了这一点。72 次计时请求中有 13 次
比其自身长度上测得的最佳速率低 15% 以上，涉及 10 个不同的长度。

这类扫描因此需要注意：

- **报告 N 次中的最佳值，而不是中位数。** 凡数据点呈双峰，中位数都会低估吞吐，
  并且完全掩盖该效应。
- **为每个数据点预热。** 使用不同唯一前缀的同长度预热请求，可使专家工作集
  保持驻留，同时仍报告提示词 token 复用为零。否则每次计时请求的代价取决于
  轮转顺序恰好把哪个数据点排在它前面。
- **长数据点会自我预热。** 在 196,608 token 及以上，请求内部会预热自身工作集，
  该干扰被冲淡；阶梯中的短点与中间点最需要预热。
- **唯一前缀只保证提示词缓存干净，别的都不保证。** 每请求使用全新前缀才是
  零复用断言得以成立的原因；它并不控制专家驻留。

## 次要观察

本次运行中，配对对等卡在低于 49,152 个新 token 时未被选中，且 32,769 token
相比 32,768 token 并无改善（4,140 对 4,264 tok/s）。已提交的
[配对卡长 prefill](../precision/paired-prefill.md) 页面记录的资格条件是每个
提示词分段的新 token 数超过 32,768，而在本机固定专家缓存的其他运行中，
32,769 token 确实发生了切分。由代价模型决定；本次运行保留了自动放置、
自适应调整与磁盘驻留，因此观测到的触发点更高。这是单次生产设置运行下的
观察，并非对该页面测量结果的修正。
